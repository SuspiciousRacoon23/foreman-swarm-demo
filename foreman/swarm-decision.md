# Swarm decision — run 0046187a

**Problem:** Create a small TypeScript library that validates Indian GSTIN numbers (15-char format + checksum) with a clean API and unit tests

**Convergence:** stopped (controller-synthesize) · 2 rounds · 4 turns · proposal confidence 0.87
**Roster (3, fallback):** tech-architecture, finance, security

## Approach
TypeScript library `gstin-validator` — zero-dependency, zero-network, dual CJS/ESM via tsup targeting ES2020. Three public exports: (1) `validate(gstin: string): boolean`, (2) `parse(gstin: string): GSTINComponents | null` returning `{ stateCode: string; pan: string; entityCode: string; checkDigit: string }`, (3) `class ValidationError extends Error { code: 'INVALID_LENGTH' | 'INVALID_STATE_CODE' | 'INVALID_PAN_SEGMENT' | 'INVALID_ENTITY_CODE' | 'INVALID_Z_MARKER' | 'INVALID_CHECKSUM' }`. A fourth export `KNOWN_STATE_CODES: ReadonlySet<string>` documents the versioned valid-code corpus. Internal-only (not re-exported from package index): `computeCheckDigit(gstin14: string): string` (verbatim GSTN spec, see f3/r1) and `generateSyntheticGSTIN(stateCode: string, pan: string): string` (test harness only). Validation pipeline strictly ordered: (1) length === 15, (2) Set lookup for state code 01–37 (no regex alternation), (3) /^[A-Z]{5}[0-9]{4}[A-Z]$/.test(chars 2–11), (4) /^[1-9A-Z]$/.test(char 12), (5) gstin[13] === 'Z', (6) checksum via `computeCheckDigit`. `validate()` returns bool; `parse()` throws `ValidationError` on any failure with the appropriate `code`, or returns typed components on success. Error messages are generic strings that do not echo, decompose, or reflect any sub-field of the input (mitigates r3). Test suite: Vitest with fixture table built entirely from `generateSyntheticGSTIN` (no real taxpayer data); must include ≥5 valid cases, ≥1 per each of the 6 `ValidationError` codes, and ≥3 checksum-mutation cases (flip last char of valid synthetic → confirm INVALID_CHECKSUM).

## Build brief
ARCHITECTURE DECISION (o1+o2, c3, c4): A single-file pure-computation library with no runtime deps is the only acceptable architecture. Any network call — even optional — introduces latency, availability risk, unmodelable per-call cost, and an unacceptable PAN exfiltration surface (c3, c4, r3). tsup dual-output (CJS+ESM) is chosen for broadest embedding compatibility without forcing a bundler on consumers.

VALIDATION PIPELINE ORDER (c1, r4): Six layers must execute in strict order with early-return on failure. Length is checked first (=== 15, not regex) to eliminate the ReDoS attack surface before any pattern matching occurs (r4). State code is validated via a pre-built Set<string> — no regex alternation — so a 14-char near-miss cannot trigger catastrophic backtracking (r4). PAN, entity-code, and Z-marker use simple character-class-only regexes with no quantifier nesting. Checksum is last because it is most expensive and only meaningful after structural integrity is confirmed. Skipping any layer produces false-positives on real invalid GSTINs (c1).

CHECKSUM IMPLEMENTATION (f1, f3, r1): `computeCheckDigit` must implement the GSTN Technical Specification verbatim: CHARSET='0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ'; for i in 0..13: v=CHARSET.indexOf(gstin[i]); p=v*(i%2===0?1:2); carry=floor(p/36)+p%36; sum+=carry; result=CHARSET[(36-sum%36)%36]. The three divergence points identified in r1 are resolved as follows: (a) multiplier sequence starts at 1 for pos-0 (odd positions get ×2), (b) carry reduction is floor(p/36)+p%36 — NOT p%36 alone — so characters S(18)..Z(35) in even positions are handled correctly, (c) final index is (36-sum%36)%36 which correctly maps 0→0 (no off-by-one when sum is a multiple of 36). This function must be cross-validated against ≥5 known-good fixtures before any other code depends on it.

ERROR TAXONOMY (c2, r3): Three remediation classes required by downstream invoice-rejection flows map to six specific codes. Structural/format failures: INVALID_LENGTH, INVALID_PAN_SEGMENT, INVALID_ENTITY_CODE, INVALID_Z_MARKER. State-code-out-of-range: INVALID_STATE_CODE (its own class per c2 — enables a distinct 'contact GST council' remediation path). Checksum failure: INVALID_CHECKSUM (signals transposition/typo — 'recheck the GSTIN number' path). Error messages are intentionally generic and must never echo, decompose, or name sub-fields of the input string to prevent leaking that the caller possesses a third party's PAN (r3).

STATE CODE CORPUS (r2): Valid codes 01–37 (current GST Council list as of 2026-06) are hardcoded in a named export `KNOWN_STATE_CODES`. The library version is explicitly tied to this corpus in CHANGELOG. If the GST Council adds codes post-publication, consumers get a silent false-negative on valid GSTINs until they upgrade — this is the accepted trade-off over a runtime fetch. Callers are advised in the README to pin a semver range and watch releases.

TEST FIXTURES (r5, o2): All GSTINs in the test corpus are synthetic — generated programmatically by `generateSyntheticGSTIN(stateCode, pan)` using fictional PANs (format-valid but not belonging to any real taxpayer). No real GSTIN is ever committed to the repo. The generator is the reference implementation of the checksum, so algorithmic drift breaks self-consistency immediately (addresses r1 and r5 simultaneously). At least 3 known-bad-checksum cases are produced by mutating the last character of a valid synthetic GSTIN, confirming the rejection path is exercised independently of generation.

## Acceptance criteria
- [ ] [guard:security] The library must make zero network calls. GSTIN validation is purely algorithmic (Luhn-variant checksum over a 36-char alphanumeric alphabet). Any outbound HTTP — e.g., hitting a GST portal to 'verify' the number — would constitute an unacceptable data-exfiltration surface and is out of scope.
